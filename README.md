# 绘本工坊（make-story-book）

把已有的故事文本做成一本绘本：自动分页 → AI 配图 → 可视化排版 → 导出 PDF。

## 环境要求

- Node.js 20+（开发用 v24.19 验证）
- Python 3.10+
- [uv](https://docs.astral.sh/uv/)

## 安装

```bash
npm run setup
```

这一步会装根依赖、前端依赖，并创建后端的 `.venv`。

**PDF 导出还需要 Chromium**（约 150MB）：

```bash
cd backend && uv run playwright install chromium
```

> macOS 上不要加 `--with-deps`，那是 Linux 专用参数。

## 配置 API Key

```bash
cp backend/.env.example backend/.env
```

然后填入 key：

| 用途 | 环境变量 | 获取地址 |
|---|---|---|
| 文本（配图提示词、改写要求） | `API_KEY` + `API_ENDPOINT` | 任意 OpenAI 兼容端点 |
| 生图（豆包） | `ARK_API_KEY` | https://console.volcengine.com/ark |
| 生图（通义万相） | 复用 `API_KEY` + `API_ENDPOINT` | https://bailian.console.aliyun.com/ |

**`API_KEY` 是"跟着 `API_ENDPOINT` 走"的**，默认指向阿里百炼，也可以指向火山方舟等
OpenAI 兼容端点：

```bash
API_ENDPOINT=https://ark.cn-beijing.volces.com/api/coding/v3
TEXT_MODEL=deepseek-v4-pro
```

两把 key 各管各的，**不能互换**：豆包只读 `ARK_API_KEY`，通义只读 `API_KEY`。

> **通义万相只在 `API_ENDPOINT` 指向 DashScope 时可用。** 它是阿里自家的服务，
> 把别家的 key 发给它只会得到 `InvalidApiKey`。这种情况下 `/api/health` 会把
> 通义标成不可用并说明原因，设置页也会禁用它——不会让你配完整本图才失败。

用 `IMAGE_SERVICE` 切换生图后端：`doubao`（默认，速度快、支持组图）或 `tongyi`。

## 启动

```bash
npm run dev
```

- 前端 http://localhost:5173
- 后端 http://127.0.0.1:8000

> 前端要用 `localhost` 访问，不要用 `127.0.0.1`——Vite 监听在 IPv6 的 `::1` 上。

打开首页会显示后端状态，包括 Chromium 是否就绪、key 是否配好。

## 架构要点

**预览和导出共用同一套 HTML 模板。** 页面渲染的唯一入口在后端
`backend/app/render/renderer.py`，产出静态 HTML。前端用 `<iframe>` 指向这个
端点做预览，导出时 Playwright 打开**同一个端点**再 `page.pdf()`。

这样做的代价是编辑器不能直接操作 iframe 内的 DOM，但换来的是：不存在"预览
好看、导出跑版"这类问题——因为根本只有一套模板。

**几何一律用 mm。** CSS 的 `mm` 在 Chromium 里固定映射 `96/25.4` px，预览与
PDF 共用同一套数字，导出时零换算误差。

**印刷版的 300dpi 落在图片上，不在页面上。** `page.pdf()` 输出的是矢量 PDF，
文字是文字不是位图。所谓高清，是指图片按**实际放置尺寸**反算 300dpi 目标像素
后重采样（`backend/app/export/image_prep.py`）。页面尺寸由 `@page` + 出血变量
`--bleed` 控制。

**uvicorn 必须 `workers=1`。** 生图任务表活在进程内存里（`services/job_manager.py`），
多 worker 时一次请求可能落到没有该任务的进程上，表现为进度条永远停在 0。

**SSE 每帧推的是完整任务快照**，前端整体替换而非增量合并。漏帧只会让进度晚
一帧更新，不会算错。断线时 EventSource 会自动重连；若任务已随服务重启消失，
前端连续几次失败后退回轮询并明确报错，而不是无限重连。

**分页不用 LLM。** 绘本必须逐字保留原文，模型会顺手润色改写。
`services/paginator.py` 只记录原文下标区间、绝不重新拼接字符串，
`check_verbatim()` 是这条不变量对应的断言。LLM 只用于"中文页文本 → 中文生图提示词"。

**提示词和画面里都不能有英文。** 这是给中国儿童看的绘本，所以生图提示词整条都是
中文（`services/prompt_builder.py`、`text_generator.py`），并且确定性拼接层里有一条
"画面中不要出现任何文字、字母、数字或标题"——只靠 LLM 指令约束不住，实测生成过
一张自带英文书名的封面。`tests/test_illustrate.py` 用 `[A-Za-z]{2,}` 扫全部风格和
版式提示，防止以后又混进英文单词（单个字母是中文用法，如"Q萌"，不拦）。

**Markdown 在入库时剥掉，不在分页时剥。** 分页的底线是逐字保留原文，它得跟
`storyText` 严格对得上；所以清理放在 `PUT /story`（`services/story_text.py`），
`storyText` 本身就是干净文本，分页不变量照旧成立。清理后的文本会随响应回传，
前端写回输入框——否则界面上显示的原文和分页出来的页面不是同一份东西。

**"转为自由拖拽"必须视觉零变化。** 预设页（CSS grid/flex）和自由页（绝对定位块）
是两套渲染方式，转换时很容易差几个像素——而用户只是想要拖拽能力，没要求改版。
所以展开逻辑集中在 `render/presets.py`，并有一条**实测**的等价性测试：
`tests/test_presets.py` 用 Playwright 把两份 HTML 都渲染出来，量元素矩形逐个比对
（文字量的是 `Range` 圈出的墨迹，不是盒子——两种模式 padding 挂在不同层级上，
量盒子会差一个 padding，但那不是视觉差异）。改 `book.css` 或 `presets.py` 后
务必跑它。

**出血是渲染时的意图，不烘进坐标。** 满版块用 `ImageBlock.bleed` 标记，坐标照
成品区记，溢出量在渲染时按模式加（预览 0mm、印刷 3mm）。把出血减进 `xMm/yMm`
会让 `object-fit: cover` 的缩放盒子跟着变，预览下的实际裁切就和预设不一致了
——而被 `overflow: hidden` 裁掉后肉眼看不出来。

**满版叠字的落点靠量，不靠猜。** `overlayPosition` 默认 `auto`：
`services/image_analysis.py` 把插图缩到 64px 宽，逐行算梯度能量，找一段最安静的
横带。生图提示词里虽然写了"下方留白"，但模型不一定听，用户换一张图留白位置也
跟着变——所以不猜，真去量。实测两张图分别把文字放到了下方的静水和上方的天空，
都避开了主体。

两个容易踩的坑，都写在代码注释里了：

- **必须先按 `object-fit: cover` 裁一次再分析。** 插图是 cover 进页面的，宽高比
  不一致时上下会被裁掉；直接分析原图，找出的"留白带"可能落在被裁掉的那一条里。
  这种错量渲染结果也看不出来——位置本身是"对"的，只是基于错误的前提。
- **分析结果照用，不要为了"离裁切线远一点"把带子往页内推。** 插画主体多半在上半
  张，空带常常本来就贴着页底，一推就整条上移、文字压到主体上。踩过这个坑：加了
  8mm 内缩，正好把文字从鱼身下沿推到了鱼身上。

**一键智能排版：算法找空地，大模型挑一块。** 上面那条自动定位只会找**全宽横带**、
只看细节量，所以「左下角一小块空白」这种答案它给不出来。排版步骤里的
「一键智能排版」是它的超集：`services/layout_analysis.py` 用二维滑窗在插图上找
任意矩形（细节量 + 彩度 + 亮度 + 底部先验，NMS 去重），把候选框连尺寸一起报给
文本模型，由模型挑一个编号并给一个和那块地方明暗相反的字色。

分工是**刻意的**，别把边界搞糊：

- **位置和颜色给模型**，因为「这块空地看着舒不舒服、字该配什么色」是判断题。
- **字号和行距由算法反算**（`services/auto_layout.py` 的 `fit_text_in_box`）。
  模型看不见字体度量：同一个"18pt"在楷体和宋体里占的宽度不同，在 297mm 宽的页和
  148mm 宽的页上更不是一回事。而框的尺寸和文字长度都是已知的，反算是闭式解。
- **只让模型选编号，不让它输出坐标。** 文本模型没有视觉 grounding，自由输出的坐标
  看起来合理但完全任意，而且**无法校验**（任何 mm 值都能被 clamp 成"合法"的，于是
  错误不可检测）。约束成编号后，失败模式从"给出了一个不可能的框"退化成"选了个不够
  好的框"，可处置性差一个量级。

**`overlay_zone_mm` 里不许出现任何图像分析。** 它在渲染热路径上（预览 iframe 每存
一次盘就重载一次），只允许读**已经存下来的** `overlayRect`；二维分析只在排版任务和
`GET /layout/preview/{n}` 里跑。这条一破，预览就会开始卡，而且很难归因。同理，
`layout_analysis`（128px 宽、二维、~20ms、只在任务里跑一次）和 `image_analysis`
（64px 宽、逐行标量、<2ms、有 LRU、每次渲染都跑）是两个模块——**性能契约不同**，
混在一起早晚有人把二维版本接进渲染路径。

**智能排版是"要么全变要么全不变"，配一次撤销。** 整件事是一次 LLM 调用加本地计算，
所以不像生图那样逐页落盘，而是最后整本一次原子写 + 一份快照
（`data/books/{id}/.undo/autolayout.json`，点开头的目录，不是用户数据）。快照存
**pages** 而不是整本书：撤销只该回退排版，不该顺手把用户期间改的标题也回滚。
恢复时**按 page id 逐个贴回去，绝不整体替换 `book.pages`**——用户可能在跑完之后
删了页、加了页、把某页转成了自由页，整体替换会删掉用户新建的页。只保留最近一次：
跑一次 → 手动调一页 → 再跑一次 → 撤销，恢复的是「手动调过的那一页」，而不是抹掉它
回到最初。

**跳过的页要说出来。** 不是满版叠字的版式、没有正文、还没有插图的页都会被跳过。
`JobItem` 为此加了第五个状态 `skipped`（区别于"处理了但失败了"），跳过原因复用
`error` 字段——进度条的 tooltip 本来就显示它。进度条上跳过的是**空心灰点**，
`Job` 的 `skipped` 计数参与"已处理"的总数，否则一本 20 页跳过 5 页的书会永远停在
75%，看起来像卡住了。

**没配文本模型 key 不是失败，是合法的降级模式。** 那时整本走纯算法路径（每个框都
用算法评分的第一名），任务照样 `done`，message 里写明"未配置文本模型，已按算法最优
位置配置"。模型调用失败也分两级：批量返回的页号集合和请求对不上就**降级为逐页调用**，
单页也问不出来才退回算法——直接把那一页用算法兜底的话，用户看到的是"大部分页智能
配了、零星几页是老的自动横带"，归因不到模型身上。

**骨架屏只在第一次加载时出现（`BookWorkspace` 里的 `bookStore.loading && !book`）。**
少了后半句，任何一次 `reload()` 都会把整块 `.body` 换成骨架屏，于是当前那一步的组件
被**卸载重建**：它持有的状态（任务流订阅、撤销栈、选中的块）全部丢掉。症状是任务跑完
后进度条连同"哪些页被跳过"一起消失，用户只看到一个一闪而过的 toast，没法回头查。

**叠字底衬是一块半透明白色圆角板，默认关掉**（`overlayPanelOpacity`，默认 0，
可在编辑器里调到 1）。之前用的是一条横跨整页、从下往上淡出的白色渐变：浅色图上
是够的，图一花就压不住，而且会把插图底部一整片洗白。换成板子之后只挡文字底下那
一块，图还看得见，字也更清楚。几何和配色都由 `render/presets.py` 定义，预设页和
转出来的自由页共用同一份——转自由拖拽后文字块必须落在白板原来的位置、带着同一块
底衬。

**但默认值是 0：不要底衬，纯靠字色压图。** 白板一铺上，画面就被切掉一块，"图"
和"字"变成两层拼在一起的东西，不像一本书。字能不能看清交给 `overlayPosition`
的自动定位（把文字挪到插图最空的那条横带里，见上一节），而不是靠盖板子。想要
底衬的用户自己在编辑器里调上去。

**默认版式是满版图叠字**（`config.DEFAULT_PRESET = "full-bleed-overlay"`），
和上面那条是配套的：整页图 + 叠字，配上自动定位的落点，就是绘本该有的样子。
底衬关掉、位置自动，这两条合起来才是"图是图、字是字地融在一起"。

**默认值一律从 `/api/meta/defaults` 取，前端不写死。** 版式下拉的初始值和
「转回预设版式」的目标都在前端，而用户点「分页」时发出去的正是**界面上那个值**
——写死的话改 `config.DEFAULT_PRESET` 界面上不会有任何变化，后端常量只管得到
新加的页。这和 `export-spec` 是同一条路子。`tests/test_meta.py` 钉住"接口报的
就是 config 里那两个常量"，默认值本身改了不该让测试红。

**楷体用霞鹜文楷（LXGW WenKai），但它是本地生成的。** fontsource 的
`lxgw-wenkai` 包只有 `-latin-` 切片，中文一个字都没有，所以
`scripts/fetch_fonts.py` 里这一项标了 `local: True`：从上游 release 下载 TTF，
再由 `scripts/subset_fonts.py` 子集化。子集化的字符集**取自已有的思源宋体 cmap**
（约 7900 字），不是另取一套——这样换字体不会出现"思源里有的字，楷体里没了"。
霞鹜文楷没有 Bold，700 字重挂的是 Medium：不这样做浏览器会自己合成假粗，
楷体的笔画一糊就完全不像楷体了。重新生成字体要装 `brotli`（fontTools 处理 woff2 需要）。

**默认字体是楷体（`config.DEFAULT_FONT_FAMILY`），改它要同时动三个地方。**
`TextStyle.fontFamily` 和 `PresetPageOptions.fontFamily` 都引这个常量（**不许各写
一份字符串**——那样迟早只改一处，表现为"新建页是楷体、重新分页出来的页是宋体"），
`render/static/book.css` 里 `body` 的兜底栈也要跟着改。兜底栈管的是**没有内联
font-family 的元素**（`.image-placeholder`、以及将来新增的），不跟上的表现是
"正文是楷体、某处一小块还是宋体"。`tests/test_meta.py` 钉住这两条不变量。

**换默认字体不会动到已有的书。** 字体族是 per-page 存进 `book.json` 的，老书里存着
老值，我们**不做迁移**——用户已经排好的书不该因为换个默认字体就整本变样。所以同一
本书里不会混（重新分页会整批重置）。`book.css` 里那几条 `@font-face` 一条都不能删：
老书数据里存着 `'Noto Serif SC'`，删了会静默回退到系统字体，预览和导出就不一样了。

3D 封面的书名也跟着书的字体走（`FlipBook3D` 的 `fontFamily`/`fontUrl` 两个 prop，
由 `BookWorkspace` 从第一页的 `options` 解析）。它拿不到 `book.pages`，所以只能靠
外面传——不传就退回宋体，那会让新书"正文楷体、封面宋体"。

**整个应用是固定高度的，滚动责任在每一页自己身上。** `html/body/#app` 是
`height: 100%`，`.app-shell` 也是 `height: 100%` + `overflow: hidden`（**不是**
`min-height: 100vh`）。以前用 `min-height` 时内容一超高就是整个 body 在滚：顶栏和
步骤条跟着一起滚走，各页面里那些 `height: 100%` 也建立在一个会变的高度上。
链条是 `.app-shell`（固定高）→ `.app-main`（`flex: 1; min-height: 0`）→ 页面根
（工作区 `.workspace`、列表页 `.page`，都是 `height: 100%`）。

工作区的 `.body` 是个 **flex 列容器**，这一点同时管着两件事：

- 想撑满整块区域的步骤（故事页、排版页）用 `flex: 1` + `margin: -20px -24px`。
  列向 flex 里负 margin 会被 flex-grow 精确补偿（outer size `0 + (-40)`，自由空间
  `(H-40) - (-40) = H`），正好等于 `.body` 的 padding box。**不能写成
  `height: 100%`** —— 百分比解析的是*内容盒*（少 40px），而负 margin 只平移不拉高，
  底部会露出 40px 灰边。`e2e_editor.py` 断言 `.body` 底边与 `.story` 底边的距离
  严格为 0，就是为了钉住这条。
- 普通文档流的步骤（设置、配图、导出）一行都不用改：它们作为 flex item
  `flex: 0 1 auto` + `min-height: auto`，主轴尺寸等于内容高且不会被压缩，内容超高
  就溢出到 `.body` 的 `overflow-y: auto`，滚动条还在窗口右缘。

⚠️ **`.app-shell` / `.workspace` / `.body` 上绝不能加 `transform` / `filter` /
`backdrop-filter` / `will-change: transform` / `contain: paint`。** 所有
`el-dialog`、`el-drawer` 的遮罩都是 `position: fixed`，靠"包含块是视口"逃过
`overflow: hidden` 的裁剪；祖先一旦有 transform，包含块变成该祖先，弹窗会被裁掉
且定位错乱。`overflow` 本身不裁剪 fixed 元素，是安全的。

**故事页是左窄右宽：左边原文，右边分页配置 + 页面列表，两栏各自内部滚。**
左栏 `clamp(380px, 34%, 620px)` 是刻意限宽的——一行一千多像素的中文没法读，
多出来的宽度全给右栏（约 1182px 视口宽以上右栏就能排两列页面卡片，更窄时自然
退成单列；硬塞两列会让每行只有 ~292px，而 `.page-head` 的固定开销就有 ~338px）。
右栏只有页面列表的卡片体在滚，「全选 / 删除选中」那行常驻。

这里**故意没有页面预览**。原来右栏挂着一块 `PagePreview`，占掉三成宽度，看的却是
"当前选中页"——而用户在这个页面要干的事是调分页参数、逐页改文字，预览帮不上忙。
连带删掉的是整套 `selected` / `keepSelected` 状态：它唯一的消费者就是那块预览，
预览没了就只剩"给卡片加个蓝边"这一个点了没反应的副作用，却要养着"删除/拆分/
合并/重新分页后让选中页指回原处"这一整类 off-by-one bug。焦点态改用
`.page-row:focus-within` 的纯 CSS 实现，键盘用户照样看得出焦点在哪一行。

**列表页的封面缩略图必须走 `.jpg?box=WxH&fit=cover` 重采样端点，不能用 `.png` 原图。**
原图单张 600~800KB，一页 12 张卡片就是 8MB，还要解码十几张 1024² 的位图。重采样
端点按 box 做磁盘缓存（`images/.resized/`）、带一年期的 `Cache-Control`，而
`imageId` 不可变，所以那个 URL 可以放心长缓存。缩略图的 `aspect-ratio` 由开本算出
（`BookSummary.trimSizeId` → `meta.trimSizes`），不这样做的话 A5 竖版的封面会被
4:3 的框裁掉上下大半。

搜索和分页都在前端做（`GET /api/books` 一次返回全部，按 `updatedAt` 倒序）：书的
数量级是"一个人写的绘本"，全量在内存里过滤是微秒级。翻页后**必须把卡片区的
`scrollTop` 归零**——那是个持久存在的滚动容器，翻页只换里面的卡片，浏览器不会
自动归零，从滚到底的第 1 页翻到只剩一张的第 2 页就会看到一片空白。

**编辑器的拖拽层和预览 iframe 共用同一个缩放变换。** `PagePreview` 把两者放进
同一个 `transform: scale()` 的容器，于是覆盖层里的坐标就是纯 mm→px，不用管缩放。
另外 iframe 上有 `pointer-events: none`——**不要删**，删掉后拖拽完全失效，
而现象是"点了没反应"，很难联想到是 iframe 把事件吞了。

**翻页预览的对开是纯前端拼的两页，后端仍然逐页渲染。** `FlipBook.vue` 并排两个
`PagePreview`，它们指向的还是同一个渲染端点——所以对开看到的就是导出 PDF 里
第 2、3 页各自的样子，不存在"对开专用模板"。含出血模式下中缝那条 6mm 正是两页
各自的 3mm 出血带，**不做合并**：合并了反而会让预览和逐页导出的 PDF 对不上。

**对开的两页必须共用一个 `zoom`，由 `FlipBook` 统一测量后传下去。** 这是整个
对开的成败点。让两个 `PagePreview` 各自 `measure()` 会有三个问题：各自的 16px
留白在中缝叠成 32px；容器按 flex 分列的亚像素取整会算出两个略不同的 zoom，两页
差一两个像素、中缝看着就是错开的；最致命的是 `.book` 的宽高是由这个 zoom **反推**
的，`PagePreview` 再去量这个"已经被缩过的容器"会形成**正反馈自缩**，几帧内页面
缩成一条线。传了 `zoom` 之后 `PagePreview` 内部的 `measure()` 结果被忽略
（它那边是 `scale = props.zoom ?? fitZoom`），反馈环不存在。
`e2e_preview.py` 断言两页 bounding box 严格等宽等高（容差 0.5px），两页不等高
时必然失败。

`zoomSlots` **不能跟着"当前屏显示几页"走**，要固定按 2 页算——否则从封面（1 页）
翻到 2-3（2 页）时页面会突然缩掉一半，看着像 bug 而不是翻页。封面（第 1 页）
单独占一屏，`rightPage` 在 `leftPage <= 1` 时返回 null，不能变成 `[1,2]` 这种
"封面和第一页并排"。

`current` 存的是**页码**不是屏序号，屏由它派生。这样单页/对开来回切时读者的位置
不会丢（在第 3 页切到对开看到 [2,3]，切回单页还在第 3 页）。右页是 `v-if` 出来的，
它挂载那一刻 `pageSize` 和 `layout` 都没变——所以 `watch` 的依赖里**必须有
`isSpread`**，否则新挂出来的右页会停在默认的 210×297，按 A4 铺开再被缩放，
看着比左页小一圈（实测左 559×794、右 794×1123，正好是 A5 与 A4 的差别）。
`nextTick` 也是必须的：`watch` 是 pre-flush，`nextTick` 回调在整个 flush
（含子组件 `onMounted`）之后才跑，那时 `rightPane` 才拿得到。

**3D 翻页的页面纹理来自后端截图，不是前端重画。** `FlipBook.vue` 里那组
「平面 / 3D」开关：平面是两个真 iframe，3D 是 `FlipBook3D.vue` 的 WebGL 翻页。
`services/page_shot.py` 用 Playwright 打开**和 iframe 预览、和 PDF 导出同一个
渲染端点**，截 `.page` 元素存成 PNG，前端拿它当纹理。前端自己用 canvas 重画
一遍页面内容的话，那才是真正的第二套模板，也正是这个项目一直在避免的事。

**默认进 3D。** 3D 现在是第一眼看到的那个"像一本书"的画面：斜放在暖色背景上、
有书脊和页口厚度、身后有柔和投影，进场时封面从右往左掀开。平面视图仍然在开关里、
仍然更锐利（纹理是位图，放大看会糊），核对排版细节时切过去 —— 但那是第二眼的事。

书的身体（书脊 / 两半页垛 / 封面封底 / 页口的一摞纸线）是**一组真实的盒子**，
不是贴图假装的：斜放时能看见页口的厚度，翻页时纸会投在下面那页上。厚度按页数线性
算，两头卡住（`STACK_MIN_MM` / `STACK_MAX_MM`）—— 太薄侧面看是一条线，太厚斜放时
页口吃掉小半个画面。

**摊开之后左右两半的厚度按阅读进度分。** 左边是已经翻过去的那摞、右边是还没翻的；
`shown.left - 1` 就是已翻页数（对开时 `shown.left` 是 2、4、6…，单页时是 1、2、3…，
一条公式两种版式通用），两块封面各自跟着自己那侧走，所以摊开时是一高一低 ——
真书也这样。总厚度守恒（右边是减出来的），不然翻到一半整本书会变厚或变薄。左右
**各有一套页口贴图**（`edgeVL/HL/VR/HR`）：厚度不同、线数就该不同，共用一套的话
薄的那侧贴图会被拉长、线变稀，看着像纸被抻了。单页模式只有右半垛可见，按进度分会
让它一路薄到没有，所以那时两边取一半。

**这个效果在现有数据下很弱，别指望能看出来。** `pageCount` 的上限是 30，而
`SHEET_MM = 0.1mm` —— 30 页正好 3mm，撞上 `STACK_MIN_MM` 的下限。也就是说
**当前所有书的总厚都恒为 3mm**，`SHEET_MM` 和 `STACK_MAX_MM` 实际是死参数（要 30 页
才追平下限、160 页才够到上限）。实测同一本 30 页的书翻到第 2 屏和第 18 屏各截一张：
差异 9,674 个像素、集中在封面边缘，**整体观感看不出区别**（封面板只移动了约 4.5px）。
要让它在视觉上真的成立，得同时调 `SHEET_MM` / `STACK_MIN_MM`，但那会改掉所有书现在
的样子，是另一个决定 —— 留着这份实现是因为厚书（或以后放宽页数上限）一来它就生效。

翻页可以**点击，也可以按住拖动跟手**（带惯性、松手按位置和速度决定翻过去还是弹回）。

几个具体的坑：

- **路径必须是 `/page/{number}/shot.png`，不能写成 `/page/{number}.png`。**
  Starlette 的路由正则是 `[^/]+`，`3.png` 会先匹配到 `/{number}`，再因为转不成
  int 而 422，根本轮不到带后缀的那条路由。
- **截图不切 `emulate_media(media="print")`**，要的是屏幕媒体，和 iframe 预览
  一致；切到 print 媒体会走 `@page` 那套，和用户在平面预览里看到的不是一回事。
- **截的是 `.page` 元素本身，不是整个视口。** 视口留白不该进纹理，否则贴到 3D
  平面上会带一圈灰边。`e2e_preview.py` 断言截图像素正好是 `页面尺寸 × scale`。
- **缓存文件名必须带内容指纹。** 只按页码存的话，用户改完文字再进 3D 预览看到的
  还是旧画面 —— 而那一版画面本身是"对"的（排版正常、字也清楚），只是内容是旧的，
  不报错也不崩溃。指纹覆盖页面**全部**字段、书级画风与角色描述、开本与出血、模式、
  倍率，外加 `APP_VERSION` 当模板变更的代理。`tests/test_page_shot.py` 逐项钉住。
- **`screenshot(path=...)` 按扩展名推断图片格式**，临时文件写成 `.png.part` 会直接
  报 `unsupported mime type`。所以先截成 bytes、写 `.part`、再原子 `replace()` ——
  并发请求可能正在读这个路径，直接写会让它读到半张图。
- **前端有纹理滑动窗口，别以为"加载过的页面纹理会一直留着"。** 页面纹理是显存的
  大头：一页 A5、`scale=2` 的 PNG 约 1118×1588，解成 RGBA 约 7MB —— 30 页的书翻一遍
  攒下 200MB。原来那个 `Map` **只增不减**（连换版式那处的 `clear()` 都没有 dispose，
  换一次版式就漏掉当时缓存的所有页），反复开关预览会一路涨到上下文丢失，而画面全程
  正常。现在只留当前屏前后各 4 页（`TEXTURE_WINDOW`）：`startFlip` 最多用到
  `right + 2` / `left - 2`，±4 留了余量，稳态下 16 张左右。
- **淘汰时"挂在那四个面上的纹理一律不删"，哪怕它在窗口外。** 翻页动画期间贴的正是
  `shown` 之外的页码（纸的正反面、掀开后露出来的那一页），按窗口一刀切会把它们抽走
  —— 现象是翻到一半的纸变成空白，而且只在特定翻页方向上复现。所以 `evictTextures`
  先收一遍 `material.map` 当白名单，再按页码距离淘汰。
- **这条断言做过反向验证。** 开着淘汰：连翻 6 屏（页码走 12 页）纹理数 `16 → 16`
  持平；把 `evictTextures()` 注释掉：`17 → 30` 一路涨、断言红。上界取 20 卡在中间
  （`TEXTURE_CEILING`）。写成绝对上界而不是"和上一屏比"，是因为翻到书末时可用页变少、
  纹理数会**下降**，拿相邻两屏比会把"降了"也判成异常。

`FlipBook3D.vue` 里也有几个不显然的点：

- **翻的是一张纸的两面，不是"一页"。** 一本书里右页 R 和它背面的 R+1 印在同一张
  纸上，所以往后翻时纸的正面是当前右页、背面就是下一页的左页；同时把"掀开之后
  露出来的那一页"（往后翻是 R+2、往前翻是 L-2）先铺到底下，纸转开时从外缘往里
  露出来。少了这一步右边会空掉半张，看着像 bug 而不是翻页。
- **两个方向都把那纸张挂在书脊右侧，差别只在旋转角**（往后翻 0 → -π、往前翻
  -π → 0）。按方向去改 `position.x` 会让往前翻的纸挂在书脊左侧、z 一路为负躲在
  页面**背后**，现象就是"往前翻没有动画"——踩过。
- **量翻页距离要用左页页码，不能用页码之和。** 封面只有一页、对开有两页，求和的
  话"封面 → 第 2-3 页"会从 2 跳到 5，明明只翻了一屏却被当成跨了好几屏，动画直接
  被跳过（实测这个 bug 让翻页从来没播过）。
- **单页屏之间也必须走"直接换"，不能落到翻页动画上。** `applyTarget` 判"要不要播
  动画"时，原来的条件是"单页 ↔ 对开**类型不同**"或"跨了好几屏"—— 漏了"旧的和新的
  **都是**单页屏"这一条。而单页屏没有书脊两边，`startFlip` 一进去就是
  `if (right === null) return`，于是 `shown` / `paintShown()` / `layout()` 一个都不
  更新：**画面一动不动，而计数器照走**（计数器在 `pointerdown` 就前进，是点击语义），
  看着就像"翻页没实现"。2 页的书（`[1,·]` → `[2,·]`）和**单页模式下的每一次翻页**
  都是这条路，后者等于整个模式翻不动。判据要写成"**只要有一边是单页屏就直接换**"，
  而不是"两边类型不同才直接换"。这个 bug 能躲过 e2e 是因为所有用例都在对开屏上跑 ——
  所以断言必须同时看计数器和 `shown`（`expect_screen`），只看计数器抓不到。
- **接上一条的后果：单页模式下每一次翻页都是瞬间切换，没有动画。** 实测过，点画布
  右半边之后 `flipMode` 全程是 `None`、`angle` 恒为 0 —— 画面直接换。这是"直接换"
  这条分支的必然结果，不是 bug，但**用户会觉得"单页模式翻页没做"**。真要做的话几何
  是现成的（`layout()` 里 `flipPivot` 在单页时已经摆在 `x=-w/2`，正好是装订边），
  缺的是 `startFlip` 里 `if (right === null) return` 那一关和"露出的是哪一页"的预铺
  —— 单页模式下没有 `rightMesh` 那个槽位，露出来的页要铺到 `leftMesh` 上。
- **动画途中再点要排队，不能丢。** `flip.to` 记住本次的目标（到落地时再读 props
  的话，途中用户又点了会直接"跳"到最新页码），`pending` 存最新目标，`finishFlip`
  落地后链式 `applyTarget` 接着翻。
- **静止弧度的量不能按"明暗差多少"来估。** `REST_CURL` 是书脊那侧页面抬起的幅度
  （相对页宽），第一版取了 4.5% —— 从正面**几乎看不出来**。原因不是量小，是它只走
  "法线偏转 → 漫射光 → 明暗"这一条路，而偏转角只有 `atan(A·π/2)`（4.5% 折合 4°），
  页面又是近白色，实测整个页面横切上蓝通道只差 1 个灰阶。真正把弧读出来的是**轮廓**：
  抬到 12% 时天头地脚那条边在中缝处比书口高出一截，投影成一道明显的折线。所以这个
  值要按"轮廓弯多少"定，不能按"明暗差多少"定。
- **弧度的方向只能是"书脊抬起"，不能是"书口垂下"。** 页面底下就是纸垛，往下垂会
  直接沉进垛里 —— 纸垛是块实心 Box，挡在页面前面，现象是**中缝两侧露出垛顶、只剩
  书脊附近一条页面还看得见**；而垛顶和纸面同色，看着只是"变暗了"，很容易当成光照
  问题查半天（当初就是这么查的）。
- **"书脊在哪一缘"是随版式变的。** 对开时左页在 `x=-w/2`、书脊在它**右缘**；单页时
  它挪到 `x=0` 独占一屏，而身体（`stackR`/`boardBack`）也在 `x=0`、包边只出在右边，
  于是装订边成了**左缘**。写死一端的现象是单页屏"书口翘起来、装订边趴平"，页面从
  纸垛上翘出去。`setSpineEnd(leftBend, ...)` 就是为这件事存在的，`layout()` 里按
  `spread` 传。
- **弯折在顶点着色器里做（`bendMaterial.ts`），注入的是 `MeshStandardMaterial` 而
  不是自己写 `ShaderMaterial`。** 项目里没有 glsl 构建配置（`vite.config.ts` 只有
  vue 插件），注入标准材质能白拿 PBR 光照、阴影和已有的色彩空间约定（贴图的
  `SRGBColorSpace` 与 `material.color` 相乘那套），自己写等于把这些重做一遍。法线
  从 `computeVertexNormals()` 换成解析解：曲面 `z = sin(uπ)·A + R·(1-sin(tπ/2))` 只有
  x 一个自由度，切向量 `(1,0,dz/du)`、法线 `normalize(-dz/du,0,1)`。两者数值上只差
  0.05%（中心差分 vs 真导数），所以换过来画面看不出变化 —— **那正是当时的验收标准**。
- **阴影用的深度材质必须跟着一起注入，这是最容易漏的一条。** `onBeforeCompile` 管
  不到阴影：three 是另外拿一张 `MeshDepthMaterial` 渲的，走的是 `mesh.customDepthMaterial`
  （平行光）/`customDistanceMaterial`（点光）。只注入表面材质的话，纸本身是弯的、
  它投出来的影子却是一块**不弯的平板矩形** —— 不报错，但一眼假。实测这条差异很大：
  有无 `customDepthMaterial` 两帧差 41,203 像素（最大差 560），而"同一份代码跑两次"
  的噪声底只有 9,192 —— 4.5 倍，而且差异的**性质**是明确的（影子左边界从竖直线变成
  跟着纸弯的斜线），不是抗锯齿。另外 `MeshDepthMaterial` 的顶点着色器里**没有**
  `beginnormal_vertex`，所以位置补丁和法线补丁必须各自自足，不能互相依赖变量声明。
- **注入过的材质必须设 `customProgramCacheKey`。** 程序缓存键里没有 `onBeforeCompile`
  这一项，three 只收 `material.customProgramCacheKey()`；更糟的是**缓存命中时
  `WebGLRenderer.getProgram` 会直接 early-out、根本不调用 `onBeforeCompile`**。不设的话，
  一个参数相同但没注入过的材质（比如垛顶那个 `paperEdge()`，它也没有贴图）会先编译出
  程序并占住缓存键，之后纸面的材质直接复用它 —— 现象是页面平的，而且只在特定加载
  顺序下复现。同理，`onBeforeUnmount` 里释放材质时也要收 `customDepthMaterial` /
  `customDistanceMaterial`：它们**不在 `mesh.material` 里**，`scene.traverse` 收不到，
  漏了就是每开关一次预览漏一张阴影程序。
- **弧度是几何上的事，e2e 别用像素去量。** 页面近白、光又漫，明暗差只有一两个灰阶，
  像素断言没有区分度。所以组件在 DEV 下把左页两端的 z 位移挂进 `__flipbook3d`
  （`pageRiseSpine` / `pageRiseFore`），`expect_rest_curl` 直接断言"书脊端有位移、
  书口端为 0"。
- **弯折搬到 GPU 之后，这两个数从"读顶点缓冲"变成了"按公式求值"**（顶点缓冲里的 z
  现在恒为 0）。**诚实地说，这条断言因此少了一颗牙**：它仍然抓得住"方向反了"，但
  **抓不住 GLSL 位移那段本身写错而 TS 侧常量没跟着改**。补轮廓断言的尝试失败了，见下条。
- **为什么不做轮廓断言：实测它测的是透视，不是弧度。** 把 `REST_CURL` 临时置 0 再量
  静止对开帧的纸面上缘轮廓（每列最上面那个非背景像素的 y，x 从 240 到 960）：

  ```
  有弧度: 187 184 182 179 177 177 171 167 164 161 160 159 158 155 153 151 148 146 143
  无弧度: 187 184 182 179 177 175 172 170 167 165 163 160 158 155 153 151 148 146 143
  差    :   0   0   0   0   0   2  -1  -3  -3  -4  -3  -1   0   0   0   0   0   0   0
  ```

  关掉弧度只让轮廓**最多动 4px**，且只在书脊附近（x≈440~680）那一段；整条边上
  44px 的斜率**全部来自书的斜放透视**，两行一模一样。照这个写断言，等于在测相机机位
  —— 有它没它都能过，是一条假测试。所以撤掉，只保留上面那条。
- **那颗牙靠"读取端独立派生"补回来。** `pageRiseSpine` 的书脊端取自**版式**
  （`props.rightPage`），不是从 `uSpineEnd` 反推、也不和 `layout()` 共用变量。共用的话
  写入端一写反、读取端跟着一起反，两个错正好抵消、断言照绿 —— 而那正是它存在的理由。
  实测过：把 `layout()` 里 `spread ? 'right' : 'left'` 故意写反，`expect_rest_curl`
  立刻红（"书脊那缘没抬起来（z=0.0000）"）；共用变量时这个场景是绿的。判据本身
  （"对开时左页书脊在右缘"）两边仍然是同一条，所以版式规则真变了不会误报。
- **纹理和 `material.color` 是相乘的。** 纸色 `0xf7f3ea` 是"还没贴图"时的占位，
  贴上白纸纹理后不退成白色的话整页会被染成米黄。反过来，加载时也要先把这一面
  退回纸色 —— 留着上一页的纹理顶着，翻页时会看见一页不该出现的内容。
- **贴图回来时要对 `mesh.userData.want`，不能比对 `shown`。** 翻页动画期间贴的全是
  `shown` 之外的页码（纸的正反面、掀开后露出的那页），比对 `shown` 会把它们统统
  挡掉，翻到一半的纸就是空白的。
- **视场角刻意开到 20°（长焦）。** 翻页时纸的自由边朝镜头转过来，34° 下这一边会被
  近大远小放大到比书还高、还顶出画面。留白系数 1.5 是按"转到约 2/3 处自由边最近"
  这个最坏情况留的：纸的自由边那时距镜头只剩 `d - w`，被放大 `d/(d-w)` 倍，要它仍
  装得下得满足 `(h/2)·d ≤ tan(vFov/2)·(d-w)²`。代入 A5 对开（w=1.48, h=2.10,
  vFov=20°）解出 `d ≥ 8.66`，而只按静态包围盒算是 5.95 —— 1.5 就是给这段留的
  （8.93 > 8.66）。斜放之后近角又朝镜头挪了约 0.54，1.35 只剩不到 1% 余量，实测会
  贴框。**这个数没有解析解**：纸是逐顶点弯出来的，没有现成的包围盒可算。
- **静止时书是斜放的，立体感全靠这个。** `REST_YAW` 取负（≈ -17°）让书口那条边转向
  镜头：绕 +y 转 θ 时 +x 面的法线变成 `(cosθ, 0, -sinθ)`，要它朝镜头就得 θ < 0。
  取正的话转过去的是书脊那侧，页口的厚度被书页自己挡住 —— 那正是改造前"看着像一张
  平面图"的原因之一。`REST_PITCH` 取负，是"从斜上方看桌上摊开的书"的角度。
  **姿态加在 `bookGroup.rotation` 上，`layout()` 里的坐标一概不动**：那些坐标都是
  `bookGroup` 的局部空间，倾斜对它们透明；`flipPivot.rotation.y` 同理（链上是
  `bookGroup.matrix · flipPivot.matrix`）。`lookAt(0,0,0)` 也不动 —— 书脊过原点，
  中缝在屏幕上的投影仍在正中，所以点左/右半边的判定和视觉中缝不会错位。
- **阴影的四个开关缺一不可，缺任何一个的现象都是"影子不出现"且不报错**：翻动的那张
  纸要 `castShadow`、下面那页要 `receiveShadow`、主光要投且**正交阴影相机罩得住**、
  `LIFT` 要够大。阴影相机给 ±2.0 而不是按书的尺寸算：纸转到一半时自由边能到书脊前方
  约一个页宽（A5 对开就是 1.0），给小了的现象是"翻到一半纸的影子突然缺一块"。
- **`LIFT` 同时是阴影贴图的分辨率门槛。** 阴影相机 4 个世界单位宽 + 1024 贴图 →
  一个纹素约 0.004；纸只抬 0.002 的话，它的影子和它自己落在同一个纹素里，会被 bias
  抹掉。0.012（1.2mm）约 3 个纹素，扣掉 `normalBias 0.004` 还剩 2 个。
- **接影子的平面用 `ShadowMaterial`，放在书背后而不是紧贴。** 背景是
  `scene.background` 画的，不参与深度，任何几何都"落"不到它上面，所以要一层专门的
  几何来接。`ShadowMaterial` 只在有影子的地方着色、其余全透明，换成
  `MeshBasicMaterial` 就会是一块灰板。放背后 `SHADOW_GAP` 处是因为影子会顺着光的
  方向偏出去 —— 那圈偏移才是"书浮在暖色背景上"的来源。
- **进场组（合着的书 + 封面）一律不投阴影。** 材质为了淡出要开 `transparent`，而
  three 对透明物体仍按不透明写深度阴影 —— 结果是封面淡到 10% 了影子还是实打实的，
  反而更显眼。书底下那圈阴影由真实的身体提供，位置几乎重合，够用。
- **进场只在首屏播"掀封面"**（`leftPage === 1 && rightPage === null`）：真书不会因为
  你跳到中间就自己合上再把封面掀一遍。别的屏走"飞入"。合着的书是**独立的一组**，
  整组淡出，而不是把真实的页面垛合起来再翻开 —— 身体的形状（一垛还是两垛、书脊有没有）
  在合/开两态根本不同。露出来的那一页和 `leftMesh` 完全重合（同一个书脊位置、同一个
  尺寸、同一个纹理缓存条目），所以交接时只有封面在消失，页面一像素都不动。
- **封面贴图是整个 3D 视图里唯一一处前端自己画的内容。** 它画的不是页面，是**装订**：
  书名、作者、一块布面底色。后端没有"封面模板"这个东西（第 1 页是普通页，不是封面），
  为了这块布面多开一个渲染端点等于凭空多一套模板 —— 那才是"页面纹理必须来自后端"
  这条规矩要防的事。字体用**和页面同一个** woff2，否则 headless 里没装中文字体会画
  出一排豆腐块，而这块封面正是进场第一眼看到的东西。
- **进场时相机从一个更近的机位退回静止机位**（`INTRO_CAM_PULL` / `INTRO_CAM_DROP`）。
  参考仓库在"合上"和"摊开"两个机位之间 lerp；我们只在进场期间有"合上"这个状态，
  所以映射成"飞入时贴得更近、掀封面时退开"，纵深更足。用的是**和飞入同一条 `eased`
  曲线**，两件事同步收尾。这里有个连带失效必须处理：`coverEdgeOnAngle()` 是
  `camera.position.z` 的函数，原来在 `layout()` 里算一次就存下来；相机在进场期间动，
  那个角就过期了 —— 现象是**封面还没侧对镜头就开始淡出**，提前露出后面那张纸。所以
  `stepIntro` 里每帧重算，`coverEdgeOn` **不能缓存**。

  这条断言的**量程**要说清：真实最大偏移是 `cameraRestZ × INTRO_CAM_PULL`（实测
  9.14 × 0.16 ≈ 1.5），但 e2e 的 RECORDER **抓不到进场最早那几帧** —— headless 里
  rAF 只有个位数帧率，`__flipbook3d` 挂上到第一次采样之间已经过了约 1/4 个进场
  （`INTRO_FLY_END = 0.42`，`eased` 到 `t = 0.42` 就饱和），那时相机只退了一成多。
  所以断言量到的是 0.14 这个**残差**，阈值按残差定 0.05，不是按全幅定。反向验证过：
  `INTRO_CAM_PULL = 0` 时红（`9.14 → 9.14`）。
- **悬停时整本书朝镜头前倾**（`HOVER_PUSH` / `HOVER_YAW`，阻尼到 `hoverAmt`）。挂在
  `hoverGroup` 上，它是 `bookGroup` 的父级 —— 姿态仍然只加在组上、`layout()` 里的坐标
  一概不动，和 `REST_YAW` / `REST_PITCH` 同一条规矩。进场期间压成 0（不然飞入的书
  一边飞一边倾，像在抖）。**这条不影响 e2e**：拖拽那组断言比的是 `progress` 和
  `shown`，不比对像素。
- **`prefers-reduced-motion: reduce` 时是跳过动效，不是"慢一点"。** 3D 这边有两处
  **前庭反应**级别的动效：进场时书从远处飞入、翻页时整张纸转 180°。开了这个开关的人
  是真的会不适。生效点三处：跳过进场（直接落终态）、翻页直接切换不做动画、关掉悬停
  前倾。`useReducedMotion()` 返回 ref 而不是读一次的值 —— 用户可能在预览开着的时候
  去改系统设置，Chromium 会派发 `change`。
  这条断言**第一版是假的**：等 800ms 后读一次 `intro`，但进场只有 1500ms、等 canvas
  又花掉几百毫秒，读到时进场早跑完、`intro` 恒为 `'none'`。改用 `add_init_script` +
  rAF 逐帧记录 `window.__intros` 才拿到 `['none', 'cover', 'none']`。假断言在反向
  验证时照样绿 —— 那正是发现它的方式。
- **拖拽的进度是增量映射，不是指针的绝对位置。** 绝对位置在按下的瞬间和当前进度对不上，
  纸会先跳一下；而且同样的手势按在画面左边还是右边，纸转的角度会不一样。行程是容器宽的
  一半，往前翻的纸从 -π 出发这件事由 `applyFlipPose` 包掉，拖拽只管把 `progress` 从 0
  推到 1，两个方向共用同一套。
- **抬手前静止了 90ms 以上就不算甩。** 少了这一步，慢慢拖到一半、停住、松手会被当成甩，
  纸"自己飞过去"，用户完全预期不到。判定顺序也是刻意的：先要朝翻页方向动过，再看
  "拖得够远"或"甩得够快"，位置优先、速度只在两端翻盘 —— 慢慢拖到 90% 再松手，速度
  几乎为 0，必须翻过去。
- **拖拽弹回时要把 FlipBook 的页码计数器一起退回去。** 计数器在 `pointerdown` 就前进
  （点击语义），只退画面不退计数器的话，用户下一次点击会从"画面显示的那屏"直接跳到
  计数器算出来的目标，中间整屏被跳过。`finishFlip` 里 `!committed && !pending` 时
  `go(-dir)` 退回去，安全性由 `applyTarget` 开头的提前返回保证（退回的目标正好等于
  `shown`，watch 那边直接返回，不会再起一次翻页）。
- **`setPointerCapture` 配套三件事，缺一个就有一半设备用不了。** `pointerup` /
  `pointercancel` 里要 `releasePointerCapture`；CSS 要 `touch-action: none`（不加的话
  触屏上浏览器会把横向拖动当滚动手势直接发 `pointercancel`，**拖拽在触屏上完全不工作
  而桌面上测不出来**）；要 `user-select: none`（否则拖拽会把文字选成一片蓝）。
- **释放几何要遍历场景，不能靠 `disposables` 数组。** `layout()` 每次都会 dispose 掉
  旧的几何换成新的，数组里存的引用早就是旧的，于是**真正在用的那批从来没被释放过** ——
  反复开关预览会按实例攒显存。`scene.background` 的贴图是遍历找不到的例外（它是
  background 不是 mesh 的 map），放进 `textures` 那个 Map 统一释放。
  `e2e_preview.py` 用"连翻 6 屏几何数必须一模一样"钉住它。
- **WebGL 在 headless Chromium 里默认就能跑**，不需要 `--enable-unsafe-swiftshader`
  （实测过）。`e2e_preview.py` 会断言 3D 画布挂得起来、默认就是 3D、进场真的掀了封面
  （逐帧记亮度）、1~5 页的纹理都从后端取过、翻页后画布还在、切回平面后画布被卸载。
- **e2e 里"拖动"这件事本身有几个坑，都写在 `drag_page` 的注释里**：一段之内不能逼帧
  （逼帧是 `Runtime.evaluate`，会插到排队的输入事件前面，pointermove 要等到下下帧才
  送达，而自动翻页只有 720ms —— 拖拽就永远接管不了）；视口要用 800×600（headless 是
  软件渲染，1440×900 一帧 300ms 上下，移动被合并得太多，同一段位移每次跑出来都不一样）；
  而**"拖一点点必须弹回"这种断言在这里根本构造不出来** —— 接管总要晚上几十上百毫秒，
  接管那一刻的进度已经不是 0 了，断言只能建立在接管之后的**相对位移**上。
  速度那两条（甩得够快就翻 / 静止了不算甩）同理测不到，留给人工。

**左右方向键翻页**（`FlipBook.vue` 的 `onKeydown`，挂在 `window` 上）。三个坑：

- **守卫只能挡文字录入，不能挡所有 `input`。** 原来是
  `closest('input, textarea, [contenteditable="true"]')`，而工具条上那 6 个
  `el-radio-button` 内层渲染的正是真的 `<input type="radio" class="el-radio-button__original-radio">`
  —— 点过任何一个之后焦点就留在上面，**此后方向键被静默挡掉**。也就是说"方向键翻页"
  以前是看运气的：开预览先点过版式开关的人，键是死的，而且不报错。
  改成白名单（`TEXT_ENTRY`：`textarea`、`[contenteditable="true"]`、以及各 `input[type=…]`
  文字类型）。用白名单而不是"排除 radio/checkbox"：以后加个开关、滑块，漏掉一个
  又是一次静默失灵，而那正是要修的那类 bug；反过来漏掉一种文字框只是那个框里
  方向键被抢，代价小得多。
- **`preventDefault()` 是承重的，别当成顺手写的。** 焦点停在 radio 上时，左右键是
  **浏览器原生**的"在本组单选里移动选中项"。实测从「单页」按左键：页面翻了，**版式也
  被切成「对开」**。这条特别阴——计数器文字碰巧还是对的（封面在单页和对开下都显示
  「第 1 / 5 页」），肉眼和 e2e 都容易漏。
  （它顺带堵的"底下的工作区跟着滚"**今天观测不到**：el-dialog 有焦点陷阱又锁了 body
  滚动，实测矮视口 + 预滚侧栏，按方向键没有任何元素滚动。留着是因为便宜，而焦点一旦
  跑到弹窗外就是真防线。）
- **全屏预览开着时，键盘归预览。** `FlipBook` 和 `EditStep` 各自在 `window` 上挂了
  keydown，两边都吃左右方向键，而 `preventDefault()` 拦不住**另一个监听器**（它只取消
  浏览器默认行为）。实测过一次 `ArrowRight`：计数器从「第 1 / 5 页」翻到「第 2-3 页」，
  **同一个块**的 `xMm` 也从 0 变成了 1 —— 静默改数据，还进了撤销栈，用户只会觉得
  "块自己动了"。用一个模块级的 `previewOpen`（`composables/previewOpen.ts`）让 EditStep
  让路，只有 `FlipBook` 写它。

  这条的 e2e（`check_preview_owns_keyboard`）**必须用自由页**：预设页上方向键本来就
  什么都不做（`if (!freePage) return`），拿预设页测等于什么都没测。

**这两条断言的"牙齿"都靠反向验证确认过，而且第一版都是假的：**

- 3D 键盘那条第一版放在 `click_half` 循环**之后**，结果把守卫改回旧写法**照样全绿**
  —— 因为 `click_half` 用真实鼠标点画布，焦点早从 radio 上移走了。现在它紧跟点完
  「单页」之后，并且**把"焦点确实在 radio 的 input 上"本身也断言掉**（`activeElement`
  的 class 里必须含 `el-radio-button__original-radio`），否则以后被人挪个位置就又变成
  一条测不到东西的假测试，而且不会红。
- 按键顺序也踩过：第一版是"左键一下、右键一下"，而**左键会走到封面**，封面在单页和
  对开下都是 `[1, None]`，两种版式分不出来 —— 把 `preventDefault()` 关掉照样全绿。
  改成**先右键**（第 2 页 → 第 3 页，单页是 `[3, None]`、对开是 `[2, 3]`，这才分得开），
  再加一条"版式单选按钮仍然高亮「单页」"。

**批量删除按下标倒序 pop，且整单原子。** 正序删会让后面的下标整体前移：删掉第 2 页
后原来的第 3 页变成第 2 页，接着删"第 3 页"就删错了。有一个越界就整体拒绝、一页
都不删——部分成功会让前端的勾选状态和实际页面对不上，而用户看到的是一句
"删了 3 页"的提示。用 `POST .../pages/batch-delete` 而不是带请求体的 `DELETE`：
后者在部分客户端和代理上不可靠。

**「生成提示词」默认跳过已有提示词的页，`overwrite=true` 才覆盖。** 批量生成时
不该覆盖用户手改过的内容；而单页「重新生成」要的正是覆盖，所以那个入口会先二次
确认再带上 `overwrite`。过滤只做一次，在 `api/illustrate.py` 里算好最终 targets
传给 `run_prompts_job`——这个函数内部**不能再过滤一遍**，否则用户明确要求的重生成
会被悄悄吃掉。

**镜头语言按页序确定性轮转，不用随机。** 画面单一（每页都是中景、平视、正面、
居中）是按同一套指令逐页生成时的必然结果。`config.DESIGN_ELEMENTS` 给景别 / 机位 /
光线 / 画面结构各列了几档，`prompt_builder.design_for_page(number)` 按页码从每组
里各取一项，拼成一句追加到提示词末尾。用**错位取模**而不是随机：随机会撞车（相邻
两页抽到同一个景别，在对开预览里正好并排显示，一眼就看出来），也**不可复现**
（同一本书重新生成一次画面语言全变，用户没法说"第 5 页那个角度好，别的页照这个
来"）。步长必须与该组长度**互质**，否则取不满一轮就开始打转（长度 4、步长 2 只会
在两个值之间来回跳）；四组长度取 4 和 5，合起来 20 页不重样。`tests/test_illustrate.py`
钉住这几条：互质、相邻页每个维度都不同、整轮覆盖每一档、同样输入同样结果。

**两层都要带这个约束：LLM 那层和确定性拼装层。** `text_generator.generate_prompts_batch`
把每页的镜头要求写进提示词，让**画面内容本身**契合（"特写"就该画脸，不是画个全景
再配句"特写"）；`prompt_builder.enhance_prompt` 末尾再追加一次。只靠 LLM 的话，
用户手改提示词、或者走 refine 路径之后这个约束就丢了；只靠拼装层的话，模型画的还是
老构图，只是末尾多了句无关的话。降级路径（LLM 不可用时的模板拼装）同样要传
`design_hints`，否则断网时又退回千篇一律。

**"300dpi"落在图片上，不在页面上。** `page.pdf()` 出的是**矢量** PDF，文字是
文字不是位图，`device_scale_factor` 只影响 `screenshot()`，对 PDF 里的文字毫无
作用。真正需要 300dpi 的只有位图插图：渲染器按块的**实际放置尺寸**反算目标像素
（`renderer.block_box_mm` / `preset_image_box_mm`），资源端点 `/api/assets/...jpg?box=WxH`
按需重采样并落盘缓存。预览和导出走**同一条**路，只是 dpi 不同（150 vs 300），
所以不需要导出前的临时文件预处理，也就没有缓存过期问题。

重采样**只缩不放**：放大不会多出细节，只会撑大 PDF。源图不够清晰时原样嵌入，
并在导出报告里如实标出"第 N 页插图有效 Xdpi（目标 300）"，让用户自己决定是重画
还是就这么印——不假装它是 300dpi。

## 常见问题

**导出的 PDF 中文变方框？**
字体没嵌入。项目使用 `backend/app/render/fonts/` 下的自托管字体，不要依赖
系统字体——浏览器预览和 headless Chromium 的系统字体可能不同。

**`/api/health` 显示 PDF 导出不可用？**
按上面「安装」一节跑 `playwright install chromium`。

**生图报 401 或 `InvalidApiKey`？**
检查 key 是否配在了对应变量上。豆包只读 `ARK_API_KEY`，通义只读 `API_KEY`，
两者的 key 不能互换。若报错来自 DashScope 而你并没有百炼账号，说明
`API_ENDPOINT` 指向的是别家——改回豆包，或换成 DashScope 的 key。

**豆包报 `SetLimitExceeded` / 429？**
账号侧配额，不是代码问题。到火山方舟控制台的「模型开通」页调整或关闭
「安全体验模式」。此时页面会被标记为 `failed` 并落一张写着"生成失败"的占位图，
不会拿假图冒充成功。

## 开发

```bash
cd backend && uv run pytest
cd frontend && npm run typecheck
```

**前端不要直接用裸 `el-slider`，一律走 `components/common/NumberSlider.vue`。**
el-slider 松手时 `emit('change')` 带的是 **props.modelValue**（旧值），而且它内部
`watch(dragging)` 在松手那一刻用 props 把自己重置回去。只读绑定
（`:model-value` + `@change`）时父组件从不回写，于是拖动中数字明明在变、一松手
弹回原值，提交上去的也是原值——看起来就是"设置按钮不生效"。`NumberSlider` 自己
接住 `update:model-value`，只在松手时用本地值 emit `change`，既拿得到新值又保持
"拖一次只提交一次"。`e2e_editor.py` 用真实鼠标拖来验这条，用 JS 改值测不出来。

**在预设页上直接拖动 = 自动展开成自由拖拽 + 把这一下接住。** 预设页没有块，
所以 `BlockOverlay` 在那种情况下退化成一块整页可抓的垫子（见其文件头注释）：
越过 4px 阈值才发起转换（单击不改模式），转换完成后拿**起点**去命中新展开的块，
松手时把累计位移作为一次 PATCH 提交。选"展开"而不是给预设页加个偏移量，是因为
展开之后这一页就拥有了整套自由排版能力——拖位置、八个手柄改大小、旋转、逐块样式，
不用再为预设页单独做一套半吊子的缩放。

两个测试文件对应两条不能破的底线，改动相关代码后务必跑：

- `tests/test_paginator.py` —— `test_verbatim_*` 断言分页结果去空白后与原文
  逐字一致。这是"不改写用户作品"的底线。
- `tests/test_render.py` —— 断言单页渲染返回的是**完整文档**（iframe 直接
  指向它）、预览版没有裁切标记、印刷版 `@page` 含出血。改渲染层前先看这里。
- `tests/test_presets.py` —— 用 Playwright 实测"预设 → 自由"的视觉等价性。
  改 `book.css`、`presets.py` 或 `page_*.html.j2` 后必跑。
- `tests/test_export.py` —— 导出是集成测试，会**真起一个 uvicorn 子进程**
  （Playwright 要用 HTTP 打开渲染端点，`TestClient` 不监听端口）。它读回 PDF
  断言页数、含出血的物理尺寸、中文能逐段原样提取，并核对印刷版按 300dpi、
  预览版按 150dpi 反算图片像素。比别的测试慢十几秒，但这是导出唯一的验收手段。
- `tests/test_assets.py` —— 重采样端点：只缩不放、cover 取两轴较小者、
  缓存键要带盒子尺寸和 fit。
- `tests/test_story_text.py` —— 剥 Markdown 的清理**不能动用户的作品**：
  没有标记的普通故事必须原样通过，`snake_case` 的下划线不能被当成强调，
  有序列表的序号故意不剥。
- `tests/test_image_analysis.py` —— 叠字自动定位：带子落在插图的哪一半。用一半
  噪声、一半纯色的合成图，断言方向对不对（只测"函数没报错"的话，"永远返回贴底"
  这种实现也能过，而那正是这个功能想避免的），以及 cover 裁切有没有被算进去。
- `tests/test_layout_analysis.py` —— 二维空白候选框：左半噪声右半纯色时最佳候选必须
  落在右半（**这是旧算法做不到、新算法的存在理由**），反过来也测一遍（防"永远返回
  右边"的假实现），全白与全中灰比亮度（直接编码"浅色背景或者白色背景"这句需求），
  以及 NMS 之后两两 IoU 不超阈值、同输入两次结果完全相同（防 NMS 里用 set 迭代序）。
  **合成图的噪声用固定种子（`NOISE_SEED`），不要改回 `os.urandom`**：候选框与横带的
  IoU 取决于框有多宽，而"哪些框活过 NMS"取决于噪声 —— 真随机时
  `test_a_better_box_is_not_thrown_away_for_overlapping_the_band` 实测 60 次红 2 次。
  测试的红绿必须只由代码决定，不能由骰子决定。
- `tests/test_auto_layout.py` —— 字号反算是**强性质测试**：对一组（字数，盒子）断言
  算出来的字号按离散公式真的放得下、而且**加 0.5pt 就放不下**，一条同时钉死"是最大
  可行字号"和"没算错"。还有行距随排满程度收紧/放松、`\n` 必须逐段算行数（按总字数
  算会低估行数、字号给大）、对比度守卫拒绝"白底白字"。
- `tests/test_layout_job.py` —— 智能排版的编排：选页（六种情况一次钉死，断言的是
  **精确列表**而不是"包含"）、模型打桩下的三级降级、以及价值最高的撤销那一组
  （按 page id 恢复、**不复活被删的页**、跑两次回到"第一次之后 + 手动调整"、
  运行中 409）。`chat_json` 的 `response_format` 不被端点支持时要去掉重试并**记住**，
  否则 30 页会挨 30 次 400。
- `tests/test_text_generator.py` —— 模型回复的解析：` ```json ` 围栏、前后有废话、
  中文键与英文别名都要认；认不出来的**返回 None 不抛**（调用方降级到纯算法），
  只有没配 key / 传输层连续失败才抛。
- `tests/test_pages_api.py` —— 拆分出来两页的 id 必须不同（`model_copy(deep=True)`
  复制的是**已生成**的字段值、不重跑 `default_factory`，所以两页会拿着同一个 id，
  前端 `:key` 撞车、`v-model` 绑错页）；批量删除删 `[2,4]` 后剩下页的 id 顺序要
  正好对上——这条专门钉倒序 pop，正序删会删错页。
- `tests/test_illustrate.py` —— 提示词生成里**不能出现英文**（`[A-Za-z]{2,}` 扫全部
  风格和版式提示，单个字母是中文用法如"Q萌"，不拦）；`overwrite=false` 时已有提示词
  的页被跳过、`true` 时被覆盖，以及全都有提示词时如实报错而不是空跑一个任务。
  镜头语言那几条（步长互质、相邻页不重复、整轮覆盖、可复现）也在这里。
- `tests/test_meta.py` —— `/api/meta/defaults` 报的必须是 `config.DEFAULT_PRESET`
  和 `DEFAULT_OVERLAY_PANEL_OPACITY` 本身（前端读的就是这两个数），以及默认版式
  确实是 `PRESETS` 里存在的键。默认值改了不该让测试红，漂了才该。
- `tests/test_page_shot.py` —— 3D 纹理的**缓存键**。它的失效是静默的：文件名只按
  页码取的话，改完文字再进 3D 预览看到的还是上一版画面，而那一版画面本身是"对"的
  （排版正常、字也清楚），只是内容旧了。所以每一条"改什么就得换指纹"都单独钉住。
  `shot_page` 本身要开 Chromium，归 `e2e_preview.py` 管。

`tests/test_geometry.py` 守住生图尺寸的边界：豆包有 3,686,400 像素的硬下限，
尺寸取整到 16 的倍数很容易掉下去，每个开本都要逐个验。

编辑器与导出有交互的部分单测覆盖不到——覆盖层与 iframe 的坐标系、指针事件接管、
缩放折算、下载链接指向的文件是否真的存在，只有真跑才知道。两个服务起着时跑：

```bash
cd backend && uv run python scripts/e2e_editor.py    # 拖拽 / 撤销 / 加块 / 滑块 / 故事页分栏与批量删除 / 列表页搜索与分页
cd backend && uv run python scripts/e2e_export.py    # 导出步骤与下载链接
cd backend && uv run python scripts/e2e_preview.py   # 翻页预览 / 单页对开 / 出血开关 / 溢出提示 / 3D 默认与进场 / 拖拽翻页 / 截图端点
cd backend && uv run python scripts/e2e_layout.py    # 一键智能排版 / 转自由后再配 / 撤销 / 存的矩形有没有进渲染
```

它们会开一个 Chromium，点真实按钮、拖真实鼠标，再回读后端落盘的数据核对结果。

`scripts/` 下另有两个**一次性数据迁移**脚本，默认只预览、加 `--apply` 才写入，
写入前会把 `book.json` 备份成 `.bak`。它们改的是已落盘的书，不是代码：

```bash
cd backend && uv run python scripts/strip_markdown_once.py   # 剥掉历史数据里的 MD 标记
cd backend && uv run python scripts/auto_overlay_once.py     # 叠字落点 bottom → auto
```

`auto_overlay_once.py` 是给"自动定位"上线之前建的书用的：`overlayPosition` 是存进
`book.json` 的，那些书里写着当时的默认值 `bottom`，不改的话用户不会自动享受到自动
定位。它只改恰好等于旧默认值的页——手动选过 `top`/`center` 的页说明用户有明确意图，
不该被覆盖。

`e2e_preview.py` 里造溢出用的正文**必须足够长**：`fit-text.js` 会先把字号降到
原大的 55% 才认输，实测 627 字在 A5 上刚好塞得下（差 3px），根本触发不了溢出。
它同时也断言了反向情况 —— 放得下时不能弹提示，否则提示会退化成"永远在响"。
